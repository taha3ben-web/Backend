# ADR-0002: نمط Outbox المعاملاتي للأحداث

- **الحالة:** مقبول (Accepted)
- **التاريخ:** 2026-07-17

## السياق

نحتاج نشر أحداث (إشعارات، تسويات، تكاملات) بشكل موثوق دون فقدانها عند فشل الشبكة
أو إعادة تشغيل الخدمة، مع ضمان اتساقها مع تغييرات قاعدة البيانات.

## القرار

اعتماد Transactional Outbox: تُكتب الأحداث (`OutboxEvent`) ضمن نفس معاملة
تغيير الحالة، ثم يرحّلها `OutboxService.relayDueEvents` (Cron كل 15 ثانية).

- توافقيّة عبر `dedupeKey @unique`.
- تراجع أسّي (`computeBackoffMs`) وحدّ محاولات `OUTBOX_MAX_ATTEMPTS = 10`.
- الأحداث الفاشلة نهائيًا تنتقل إلى DLQ (حالة `DEAD`) وتُرصد.

## البدائل المرفوضة

- طابور خارجي (BullMQ/Kafka): يضيف بنية تحتية وتبعيات؛ الـ Outbox الدائم يكفي للحمل الحالي
  ويضمن الذرّية مع قاعدة البيانات.
- نشر مباشر داخل المعاملة: يربط نجاح المعاملة بتوفّر طرف خارجي (هش).

## التبعات

- رؤية وصيانة الطابور عبر وحدة `queue-insight` (المرحلة 74) ومركز العمليات.
- تنظيف الأحداث المُسلّمة يعتمد فهرس `OutboxEvent(status, deliveredAt)` (المرحلة 77).

## المراجع

`src/common/infra/outbox.util.ts`، `outbox.service.ts`، `infra.module.ts`؛ نموذج `OutboxEvent` / `OutboxStatus`.
